# Changelog — quiltmc-1.20.1-generator (Lightseeking build)

First community-built Quilt 1.20.1 code generator for MCreator. This is a
ground-up implementation (not a patch over an official quilt generator, since
Pylo/MCreator never shipped one). Semantics are cross-referenced from the
official Forge 1.20.1 and NeoForge 1.21.1 generators.

Release cycle naming:
- `1 周目` → basic mod elements are mostly complete and functional
- `2 周目` → global triggers are mostly complete and functional
- `3 周目` → triggers for basic mod elements + remaining details are mostly complete
- `4 周目` → LICENSE / release metadata preparation

All changes are released under GPLv3 (see `LICENSE`). MCreator's
"Additional permission for code generator templates (*.ftl files)" is
**retained**, so the code generated by this patched generator (the
end-user's own `src/` directory) does not itself become GPL-infectious;
modders can keep licensing their generated mod code however they like.

## v1.1.0-demo — 2026-08-15 (htqkeku @ Lightseeking(FL) Studio)

### Dimension system
- **Fix** `DistanceManager.removePlayer` `NullPointerException` when a
  ServerPlayer is transported to a custom dimension. The original
  `entity.changeDimension()` call produced NPE inside Quilt's
  DistanceManager. The portal code path now uses `ServerPlayer.teleportTo()`
  and manually fires the dimension-change procedure callbacks.
  → `templates/dimension/blockportal.java.ftl`
- **Fix** dimension enter/leave procedure triggers fire **twice**.
  The listener in `dimension.java.ftl` was removed and only the explicit
  callback inside `blockportal.java.ftl` remains.
  → `templates/dimension/dimension.java.ftl`
- **Fix** dimension event listeners were not self-registering when the
  `XxxModDimensions` container class was missing / not generated.
  Dimension files now carry a `static {}` initializer that calls
  `LivingEntityEvents.ENTITY_TRAVELS_TO_DIMENSION.register(...)` directly.
  → `templates/dimension/dimension.java.ftl`

### Lightning bolt trigger
- **Fix** "when entity is struck by lightning" procedure trigger fires
  **continuously** / multiple times for the same strike. Replaced the
  `WeakHashMap`-based flag with a `ConcurrentHashMap.newKeySet()` of
  UUIDs that tracks which entity-strike pairs have already been handled
  this tick.
  → `templates/mixin/lightning_bolt_mixin.java.ftl`

### AI tasks
- **Fix** AI goal `[Attack entity of type ()]` causes runtime crash when
  the matching procedure slot is empty. Generator now emits the 3-arg
  `NearestAttackableTargetGoal(Entity, Class, boolean)` constructor and
  guards generation behind a has-content check so no zero-arg variant
  (which does not exist) is emitted.
  → `aitasks/attack_entity.java.ftl`

### Potion / MobEffect system
- **Fix** "on mob effect started / applied" procedure never triggers.
  The effect class now fires the user procedure from two paths:
  from `addAttributeModifiers(...)` (for normal duration effects) and
  from `applyInstantenousEffect(...)` (for instant effects). A single
  boolean `th$started` guard ensures the start procedure only runs
  once per stack application.
  → `templates/potioneffect.java.ftl`
- **Fix** "every tick" procedure still runs when the user marks the
  effect **instantaneous**. Generator now emits `applyEffectTick(...)`
  only when `!data.isInstant`.
  → `templates/potioneffect.java.ftl`
- **Fix** "when effect expires" procedure never fires when the entity
  **dies** while still under the effect. `XxxMobEffects.init()` now
  registers `ServerLivingEntityEvents.AFTER_DEATH` and runs the
  matching onExpired callback for any effect that the entity still has
  at the moment of death.
  → `templates/elementinits/potioneffects.java.ftl`

### Mod bootstrap
- **Fix** generator emits `${JavaModName}Procedures.registerProcedures()`
  even when the workspace contains zero custom procedures → class not
  found compile error. The call is now wrapped in a Freemarker
  filter that requires at least one procedure element.
- **Fix** `${JavaModName}DispenseBehaviors.init()` is likewise only
  emitted when at least one item extension has dispenser behaviour.
  → `templates/modbase/mod.java.ftl`

### Dispenser / item extension
- **Fix** "when dispenser attempts to dispense" procedure is never
  invoked. The attempt callback is now called at the **very top** of
  `DispenseItemBehavior#execute(BlockSource, ItemStack)` for both the
  `OptionalDispenseItemBehavior` wrapper and the default direct
  subclass path. Two field name variants (`dispenseAttemptedProcedure`,
  `dispenseAttemptProcedure`) are checked for MCreator cross-version
  compatibility; missing dependencies are logged to
  `System.err` if the procedure signature doesn't match.
  → `templates/elementinits/dispensebehaviors.java.ftl`
- **Fix** Forge-only `ItemHandlerHelper.giveItemToPlayer(...)` used in
  the "give entity item" procedure snippet causes compilation failure
  on Quilt / Fabric. Replaced with vanilla
  `Player.getInventory().add(ItemStack)` + a fallback
  `world.addFreshEntity(new ItemEntity(...))` drop when the inventory
  is full, matching the behavior Forge users expected.
  → `procedures/entity_add_item.java.ftl`

### Fuel / Furnace burn-success condition
- **Fix** "fuel burn-success condition" is ignored at runtime. The
  Quilt/Fabric `FuelRegistry` is a static registry that cannot encode
  runtime predicates; the generator previously accepted the procedure
  but never emitted it anywhere. Solution:
  1. `XxxItemExtensions` now exposes a static method
     `int checkFuelBurnCondition(ItemStack fuelStack, Level, BlockPos)`
     that walks every fuel extension with a non-trivial
     `fuelSuccessCondition` / `fuelBurnCondition` procedure, evaluates
     the condition, returns `0` to refuse burning, and supports
     two return-value conventions for the condition procedure –
     boolean (default GUI picker) and `ItemStack` (manual XML binding).
     → `templates/elementinits/item_extensions.java.ftl`
  2. A new Mixin on `AbstractFurnaceBlockEntity.serverTick` hides the
     fuel slot at `@At(HEAD)` (only when the furnace is currently
     **unlit** – so a burn that is already in progress is never
     interrupted) and immediately restores the saved stack at
     `@At(RETURN)`. Because the whole hide/restore happens inside a
     single tick, the client never sees an empty slot, but
     `serverTick` itself cannot pick up a new fuel for ignition while
     the user's condition says "refuse". `ConcurrentHashMap` strong
     references guarantee the saved stack is never lost to GC. When
     the condition transitions from `false` → `true`, the following
     tick proceeds to normal burning.
     → `templates/mixin/abstract_furnace_block_entity_mixin.java.ftl`
- Note: the MCreator GUI dropdown for "burn-success condition" only
  accepts boolean-returning procedures today; the `ItemStack` return
  branch inside `item_extensions.java.ftl` is kept as a compatibility
  hook for users who are comfortable patching the workspace XML
  directly, and causes zero overhead when unused.

### Structure / Feature / worldgen system
- **Fix** `TestXxxFeature.java` fails to compile because
  `featuretype` was explicitly `<#assign>`'d to an empty string
  inside `feature.java.ftl` and
  `configured_feature.json.ftl`, overwriting MCreator's built-in
  `featuretype` loop variable. Generated code became
  `public class XxxFeature extends {` and `super(.CODEC);` which
  are syntactically invalid. Explicit `<#assign>` was removed from
  all four files; the built-in variable is used directly.
  → `templates/feature/feature.java.ftl`,
    `templates/feature/configured_feature.json.ftl`,
    `datapack-1.20.1/templates/feature/configured_feature.json.ftl`,
    `datapack-1.20.1/templates/feature/placed_feature.json.ftl`
- **Fix** generator emits `world/features/StructureFeature.java`
  and `StructureFeatureConfiguration.java` with **zero imports**,
  causing `Codec`, `BlockPos`, `Holder`, `RandomSource`,
  `WorldGenLevel`, `Mirror`, `Rotation`, `Feature`,
  `FeaturePlaceContext`, `BlockIgnoreProcessor`,
  `StructurePlaceSettings`, `StructureTemplate`,
  `StructureTemplateManager` to all be reported as "cannot find
  symbol". Full import blocks were added matching the official
  forge-1.20.1 templates.
  → `templates/feature/structure_feature.java.ftl`,
    `templates/feature/structure_feature_configuration.java.ftl`
- **Fix** `XxxFeatures.java` never registers the custom
  `StructureFeature` class into `BuiltInRegistries.FEATURE`. Any
  workspace that used a "Feature (structure)" element therefore
  died with a `NoSuchElementException` / missing registry entry at
  runtime because the `configured_feature.json` referenced a
  feature type that was not registered. `STRUCTURE_FEATURE`
  static field + `Registry.register(...)` line restored from the
  official forge version.
  → `templates/elementinits/features.java.ftl`
- **Fix** `generator.yaml` spelled the structure NBT target
  directory as `@MODDATAROOT/structure` (singular). Minecraft's
  `StructureTemplateManager` (used by the Structure Block, `/place
  jigsaw`, and the Jigsaw pool resolver) only looks inside
  `*/structures/*` (plural) both on the server-side resource pack
  (`data/<namespace>/structures`) and the client-side resource
  pack (`assets/<namespace>/structures`). As a result, MCreator
  copied every user-supplied `.nbt` into a directory that Vanilla
  never read, and the Structure Block reported
  "No structure named '<id>' exists". The key is now aligned to
  the official forge-1.20.1 value:
  `structures_dir: "@MODDATAROOT/structures"`.
  → `quilt-1.20.1/generator.yaml`
- **Fix** even when `structures_dir` (above) is correct, the
  Structure Block / StructureTemplateManager still loads templates
  via `ResourceManager` which in 1.20.1 scans only
  `assets/<namespace>/structures/*.nbt` for server-side templates.
  Meanwhile MCreator (and the generator) copy `.nbt` files only to
  `data/<namespace>/structures/` so that worldgen JSONs can
  reference them – the two locations are disjoint and the
  Structure Block therefore never finds the template. The patched
  `workspacebase/build.gradle` adds a `processResources.doLast`
  action that mirrors every `data/<ns>/structures/*.nbt` (plus the
  legacy singular directory as a migration safety net) into
  `assets/<ns>/structures/` after every resource build, so both
  the Jigsaw JSON worldgen path AND the interactive Structure
  Block path find the same template.
  → `quilt-1.20.1/workspacebase/build.gradle`
- **Fix** PowerShell's `Set-Content` silently prepends a UTF-8
  BOM when patching `build.gradle` on Windows, and Gradle
  aborts with `Unexpected character: '﻿' @ line 1, column 1` on
  the next build. Both the runtime patcher (when invoked locally)
  and the generator template now emit the file via
  `[System.IO.File]::WriteAllText(..., new UTF8Encoding(false))`
  which writes UTF-8 **without** a BOM.

### Armor / item description localization
- **Fix** custom armor items show the raw translation key
  `item.<modid>.<registryname>_helmet.description_0` instead of
  the user-entered description text in the item tooltip. The
  reason: `armor.definition.yaml` on the quilt side had dropped
  **all four** `localizationkeys.fromlist` entries for helmet /
  chestplate / leggings / boots fixed descriptions. MCreator's
  generator never emitted the matching `description_<i>` keys
  into `lang/zh_cn.json` / `en_us.json`, so vanilla fell back to
  printing the untranslated key. All four `fromlist` lines and
  the four item-name `condition` guards were restored from the
  official forge-1.20.1 definition, plus `chestplateName` was
  corrected to map to `bodyName` because MCreator internally
  stores the chestplate label under that field name.
  → `quilt-1.20.1/armor.definition.yaml`
- **Added** armor-related templates to the set of files synced by
  `fix_mcreator_templates.ps1`: `armor.java.ftl`,
  `json/armor_model_{helmet,chestplate,leggings,boots}.json.ftl`,
  `json/armor_trim.json.ftl`, and `utils/triggers.java.ftl`
  (which contains the `addSpecialInformation` macro used by
  armor description lines).

### Helper scripts
- **Fix** `fix_mcreator_templates.ps1` failed silently on Windows when
  the project path contained non-ASCII characters
  (`mcreator扩展制作skill`) – `Join-Path` + default PowerShell
  encoding produced mojibake paths and every copy showed `MISSING
  SRC`. The script now anchors everything to a literal short-path
  (`DOWNLO~1\MCREAT~1`) and uses `-LiteralPath` everywhere, and any
  missing source file is reported in red `[MISSING SRC]` so a broken
  copy cannot be mistaken for a successful one. The script also now
  covers the `aitasks/*.java.ftl`, `procedures/*.java.ftl` and
  root `itemextension.definition.yaml` directories that were not
  part of the initial copy list.
